Reading a product's warranty and registering the product require different kinds of access to a website. A public page may answer the first request. The second may require a login, a form, and confirmation that the registration went through. This study of 50,000 domain names examines what software can find through public web requests. It reports 61 checks for text, resource lists, and possible ways to use online services. The study recorded check results; it did not test whether agents finished a task.

## 1. Readiness depends on the task

AI agents use models to choose actions and software tools to carry them out. A model can choose to open a page, read the reply, and then follow a link. [Anthropic's guide to agents](https://www.anthropic.com/engineering/building-effective-agents) describes this use of tools and feedback. The tools can include a browser or an application programming interface, usually called an API. An API lets one program ask another for data or an operation. [OpenAI's July 2025 ChatGPT agent announcement](https://openai.com/index/introducing-chatgpt-agent/) describes a product that offered both browser tools and API access.

A browser can run a page's scripts, follow links, and fill in forms. A program making direct HTTP requests receives replies without running those scripts. A request carrying a user's account credentials may reach pages closed to a public request. Here, a client means the program making the request. Its tools and permissions affect what it can do, even when the website stays the same.

The analysis counts saved check results and compares them across rank groups and repeat attempts. The study chose these comparisons after the data were available. [WebArena](https://arxiv.org/abs/2307.13854) instead checks whether an agent gives the right answer or makes the requested change on a controlled website. A claim about an agent's work needs that kind of checked outcome.

## 2. Which domains were checked, and when

The sample comes from the first million entries of [Tranco list ZJQ6G, generated on September 2, 2026](https://tranco-list.eu/list/ZJQ6G). Tranco combines several rankings into a list for research. This study divides that list into three groups by rank. Rank alone does not describe what a site does, who owns it, or whether it suits a task.

| Rank range | Domains in the full list | Sampled domains |
|---|---:|---:|
| 1-10,000 | 10,000 | 10,000 |
| 10,001-100,000 | 90,000 | 20,000 |
| 100,001-1,000,000 | 900,000 | 20,000 |

The sample includes every domain in the highest-ranked group. The other groups use random draws, with no domain picked twice. The seed `20260903` allows the same draw to be repeated. All 50,000 sampled names have a final record with all 61 check labels. Failed, warning, and not-applicable results remain in the analysis, including domains whose homepages fail the text check.

The saved final results span 18.77 hours on September 3-4, 2026 UTC, including repeat scans. Each listed hostname counts once. Several names may lead to the same website, and some serve technical systems rather than public pages. The counts therefore describe domain names, not distinct businesses or website owners.

The sample gives highly ranked domains more weight than they have in the full list. The top group makes up 20% of the sample but only 1% of the list. Section 11 adjusts for this difference. Those estimates still concern the named Tranco list, which does not cover the whole internet.

## 3. Why there are 61 checks

The checklist covers public content, possible service interfaces, page descriptions, security headers, and payment-related text. An interface is a way for software to request data or an action. A header is information a server sends alongside its reply. Resource lists can help locate content, while API descriptions explain how to use a service. A payment marker may matter for a purchase but have no bearing on reading a public report.

| Category | What the checks look for | Checks |
|---|---|---:|
| Discovery | Resource lists, crawler rules, guidance files | 13 |
| Access | Response codes, text, formats, response headers | 9 |
| Interfaces | API descriptions, protocol markers, access information | 10 |
| Security | Headers and contact details | 11 |
| Metadata | Titles, language labels, structured page descriptions | 15 |
| Payments | Payment-related headers, text, and terms | 3 |

The [development record](https://github.com/vedangvatsa/vedang-website/commit/4ea4f34100157ae75e38baa935fd855930180179) describes combining an AI-standards checklist with a general website checklist. Later changes added checks related to AI search, agents, search engine optimization, and citations. Code versions contain 32, then 52, then 61 named checks. The 61-item version has a recorded commit date before the September measurements.

The count depends partly on how results are grouped. One check looks for a basic Model Context Protocol (MCP) response; another looks for its capabilities field. MCP defines how software exchanges information about tools and resources. The two crawler-named requests, by contrast, produce one combined check. The number 61 describes this chosen set. The development history does not show that it is the best set for predicting whether an agent will finish a task.

The analysis keeps every recorded check, including those with few or no passes. The [check-by-check supplement](/papers/agentready-check-selection.txt) explains each item's purpose and limits. It separates published formats from filenames and cutoffs chosen for this checklist.

## 4. What a pass means

The request details come from [saved source code](https://github.com/vedangvatsa/vedang-website/commit/ea0e797ecc13e494968500db03f128679f05b92b) with the same check names and record format as the results. The records do not state the exact code version run for each scan. The saved code explains the rules and allows tests of how they behave.

For each domain, the code starts 34 fetch operations and can try up to six extra resources. A fetch asks the server for a resource. Redirects can make one fetch produce several network requests. Each fetch has a 4.5-second timeout. The code requests the HTTPS homepage and addresses such as `/robots.txt`, `/llms.txt`, and `/openapi.json`. It also asks for Markdown, a plain-text format that can include headings and links. Two homepage requests carry GPTBot and PerplexityBot names in the user-agent header, which identifies the requesting software. The code does not log in or run page scripts.

Several checks reuse the same reply. Others read a different address, a header, or part of the input URL. A pass means that the input matches the rule. A warning can mean a partial match or a missing signal. A not-applicable label can mean that an optional signal was absent or that the check depended on another result.

The records save labels, scores, scan times, and durations. They leave out full reply contents, individual request codes, detailed errors, and redirect histories. These missing fields prevent later checks of what each server returned. They also prevent trying a different text-length cutoff on the old replies.

## 5. Text and server replies

The text check passed on 22,855 domains, or 45.71%. It removes scripts, styles, and HTML tags, reduces repeated spaces and line breaks, then requires more than 300 characters. It reads the ordinary homepage reply. If that reply is empty, it uses the reply to the Markdown request. The code uses JavaScript's string length, measured in UTF-16 units, so some visible characters count as two.

Hidden text and error messages can add to the count. A short page can answer a question fully and still fail this rule. The 45.71% result therefore measures a length test, not whether an agent understood the page.

| Result | Domains | Share of all 50,000 |
|---|---:|---:|
| Text-length check passes | 22,855 | 45.71% |
| Both crawler-named requests return HTTP 200 | 18,912 | 37.82% |
| Exactly one returns HTTP 200 | 3,901 | 7.80% |
| Neither returns HTTP 200 | 27,187 | 54.37% |
| Text check passes and both requests return HTTP 200 | 15,080 | 30.16% |

HTTP 200 means the server returned an "OK" status. It does not establish what the reply contained. The last row combines the text result with the two named-request results for each domain. Those results came from separate requests, rather than a single attempt to read a page.

The test program supplied the crawler names; these were not verified visits by the companies' own crawlers. The neither-success group includes both non-200 replies and failed fetches. Its labels cannot distinguish firewall decisions, timeouts, connection errors, or other causes.

The [Robots Exclusion Protocol](https://datatracker.ietf.org/doc/html/rfc9309) lets sites publish rules for crawlers. Those rules do not grant an agent permission to change an account or make a purchase. The study's robots check looks for selected text patterns rather than fully interpreting the file's rules. A pass cannot establish that a site permits a particular client or action.

## 6. Finding resources beyond the homepage

The sitemap-and-robots check passed on 13,686 domains, or 27.37%. A sitemap lists page addresses. This check looks for sitemap text markers and a sitemap declaration in `robots.txt`.

The JSON-LD check passed on 10,687 domains, or 21.37%. JSON-LD is a format for adding linked data to a page. The rule looks for blocks labelled as JSON-LD and tests whether at least one can be read as JSON, the underlying text format. Reading that structure does not check whether the data follows all JSON-LD rules or describes the page correctly.

The [`llms.txt` proposal](https://llmstxt.org/) describes a Markdown file with information about a site. The study's rule requires a minimum length, a heading, and link syntax at the tested addresses. It passed on 3,310 domains, or 6.62%. The Markdown-response rule passed on 1,474, or 2.95%. A separate length rule for `/index.md` passed on 5,337, or 10.67%. These checks test different ways of requesting text.

Among domains that failed the homepage text rule, 452 still passed the `llms.txt` check and 2,231 passed the sitemap check. Keeping only text-passing domains would remove 13.66% of the recorded `llms.txt` passes, 16.30% of sitemap passes, and 20.26% of the domains passing both named requests. A failed homepage check is therefore a poor reason to discard results from other addresses.

The text and JSON-LD rules read the same selected page body, and the text rule can use the Markdown reply. Agreement between checks does not always reflect separate features that a website owner chose to provide.

[Ahrefs reported](https://ahrefs.com/blog/llmstxt-study/) that 97% of detected `llms.txt` files among 137,210 domains using its Web Analytics service received no requests during May 2026. A published file may go unused. Ahrefs studied a different group of sites with a different method, so its result does not validate this study's matches.

## 7. Which checks pass together

The separate percentages do not show how many domains pass several checks. This comparison counts passes for `llms.txt`, Markdown responses, and the basic MCP marker on the same domain. The three concern guidance, another content format, and a possible tool interface. None is required for every agent task.

| Number of selected checks passing | Domains | Share |
|---|---:|---:|
| None | 46,252 | 92.50% |
| One | 2,635 | 5.27% |
| Two | 280 | 0.56% |
| All three | 833 | 1.67% |

At least one passed on 3,748 domains, or 7.50%. Adding the three separate pass counts would count some domains more than once. The 833 domains passing all three account for 91.54% of the 910 basic MCP matches. The Markdown rule passed on 32.60% of domains passing `llms.txt`, compared with 0.85% of the remaining domains.

Sites may publish these resources together. A server may also return the same content from several addresses. Prepared tests show that such replies can pass multiple checks. The saved labels do not show how much each explanation accounts for the overlap.

## 8. Finding a service and testing whether it works

The basic MCP check sends a request to start a session at two possible addresses. It looks for `jsonrpc` in a reply with a status code from 200 through 299, known as HTTP 2xx. This rule passed on 910 domains, or 1.82%. The [MCP specification](https://modelcontextprotocol.io/specification/2024-11-05/basic/lifecycle) describes further steps for agreeing on versions and capabilities before using a tool. The check stops at a text match in the initial reply.

Only three of those 910 records also passed the JSON-and-capabilities rule; 907 received a warning. That rule tries to read the whole reply as one JSON document. [MCP's later HTTP transport](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports) also permits replies sent as a stream of events. A prepared example in that format passed the basic rule but received a warning from the capabilities check. The two checks can also select different replies. The warnings alone do not show whether a service exists or works.

The OpenAPI rule matched 78 domains, or 0.16%. An [OpenAPI description](https://spec.openapis.org/oas/v3.1.2.html) can list a service's operations, required inputs, and replies. This check searches possible description files for a version field or text marker. It does not validate the whole file or test an operation. The service may also publish its documentation at an address outside the short list that the code tries.

Payment-related markers appeared on 163 domains, or 0.33%. The study made no payments. A site that only supplies public information may have no reason to publish a payment marker. These counts say where the chosen rules matched; they give no success rate for purchases, bookings, or account changes.

## 9. Similar scores can come from different checks

The final average scores are 26.1, 25.2, and 25.9 across the three rank groups. Those averages are close, but the individual checks differ. The `llms.txt` pass rate is lowest in the middle group. Markdown and MCP-marker pass rates rise toward the lowest-ranked group.

The program divides earned points by a maximum that depends on which checks apply. Optional checks can add points without raising that maximum. The input-HTTPS rule adds three points per domain because its input URL starts with HTTPS; it never tests the connection. Equal totals can therefore come from different passed checks. The full-sample average is 25.7, and the median, or middle score, is 22. The study did not test whether these scores predict task success.

## 10. Rechecking low scores changes the comparison

All 21,547 domains whose earlier score was ten or below received another scan. Higher-scoring domains kept their earlier records. The final file uses the newer result even when its score fell.

Scores increased on 5,965 rechecked domains, decreased on 553, and stayed unchanged on 15,029. Across the full sample, the average rose from 22.68 to 25.69. The 3.00-point change uses the values before rounding. Most rechecked scores stayed the same, even though the average rose.

| Check | Pass gains | Pass losses | Net change over all 50,000 |
|---|---:|---:|---:|
| Text-length rule | 3,629 | 0 | +7.26 percentage points |
| Both requests classified HTTP 200 | 3,018 | 16 | +6.00 percentage points |
| llms.txt | 467 | 5 | +0.92 percentage points |
| Markdown | 171 | 0 | +0.34 percentage points |
| MCP marker | 84 | 0 | +0.17 percentage points |

Only one rechecked domain had originally passed the text rule. Almost none of the rechecked records could therefore change from a pass to a failure. Zero lost passes does not show that results stay the same over time. Testing that would require repeating scans of high-scoring domains as well as low-scoring ones.

Rechecks covered 52.44%, 43.12%, and 38.40% of the highest, middle, and lowest rank groups. Their earlier average scores were 20.7, 22.4, and 23.9. The highest-ranked group started below the lowest-ranked group and finished above it. Their final averages partly depend on which domains were tried again.

## 11. Adjusting for the full list's mix of ranks

The three rank groups make up 1%, 9%, and 90% of the full Tranco list. Weighting gives them those shares when combining their results. The lowest-ranked group accounts for 40% of the sample but 90% of the full list. Checks that pass more often in that group get larger estimates after this adjustment. The estimates assume the same collection procedure under comparable conditions across the full list.

| Check or combination | Share in the sample | Estimate for the full list | 95% sampling range |
|---|---:|---:|---:|
| Text-length check | 45.71% | 46.58% | 45.96%-47.20% |
| Text and both HTTP-200 conditions | 30.16% | 29.91% | 29.35%-30.48% |
| Sitemap and robots markers | 27.37% | 27.54% | 26.98%-28.09% |
| JSON-LD check | 21.37% | 20.67% | 20.16%-21.17% |
| llms.txt check | 6.62% | 7.35% | 7.02%-7.67% |
| Markdown response | 2.95% | 3.90% | 3.65%-4.14% |
| MCP marker | 1.82% | 3.18% | 2.96%-3.41% |
| OpenAPI marker | 0.16% | 0.10% | 0.06%-0.13% |
| At least one selected check | 7.50% | 8.09% | 7.75%-8.43% |

The adjustment raises the MCP estimate and lowers the OpenAPI estimate. Text, sitemap, and JSON-LD checks still pass more often than the selected guidance and interface checks under both rank mixes.

The 95% ranges describe uncertainty from sampling only some domains in the lower two groups. The calculation accounts for how much of each group was sampled and treats saved results as fixed. Since every top-10,000 domain was included, that group has no sampling uncertainty. The ranges exclude mistaken matches, changing request outcomes, and uncertainty about rechecks. The 95% level applies to each range separately, not to the table as a whole. The paper gives the full calculation.

## 12. Comparing domains listed in CrUX

The July 2026 Chrome User Experience Report (CrUX) list contains matches for 23,592 sampled names. For this comparison, the study ignores the URL protocol and port and treats names with or without a leading `www` as the same. [CrUX entry rules](https://developer.chrome.com/docs/crux/methodology) include popularity and whether pages can be found on the public web. [Tranco also uses CrUX as a source](https://tranco-list.eu/methodology).

CrUX-listed domains pass the five checks below more often within every rank group. The adjusted comparison gives listed and unlisted domains the same rank mix: 20% from the top group, 40% from the middle group, and 40% from the bottom group. These are the shares in the sample.

| Check | Gap after giving both groups the sample's rank mix |
|---|---:|
| llms.txt | +4.66 percentage points |
| MCP marker | +2.54 percentage points |
| Both HTTP-200 conditions | +15.64 percentage points |
| Markdown | +2.50 percentage points |
| robots.txt rule | +21.22 percentage points |

CrUX-listed domains also have higher rates when the calculation uses the full-list mix of 1%, 9%, and 90%. The broad rank groups do not explain the whole difference. The study does not measure site type or account for every difference within those groups. CrUX's entry rules may also matter. These comparisons cannot show that traffic caused the higher pass rates.

## 13. Where the checks can give misleading results

After data collection, the study tested the saved code with thirteen prepared cases. Seven are shown below.

| Prepared input | Observed result |
|---|---|
| Every fetch raises an error | All 61 labels produced; score 6 |
| Empty HTTP 404 replies | Same labels as the all-error case |
| Long HTTP 403 page | Text rule passes |
| Short ordinary HTTP 200 page | Text rule fails |
| Same generic HTML at every address | 23 passes; score 47 |
| Successful error reply containing jsonrpc | Basic MCP marker passes |
| MCP capabilities inside an event stream | Basic marker passes; capabilities check warns |

The same 61-label pattern produced by the all-error and empty-404 cases appears in 14,776 real records, or 29.55%. The labels alone cannot tell whether either cause, or something else, produced those results. Those domains remain in the sample. The prepared tests show possible errors but do not measure how often they occurred among real websites.

[Thunderbit reported](https://thunderbit.com/blog/llms-txt-website-trend) 1,606 HTTP-200 results at tested `llms.txt` addresses among 10,000 Tranco domains, but accepted only 586 files after checking their contents. An address can return an ordinary page instead of the requested file. Thunderbit's sites and rules differ from this study's, so its figures cannot independently confirm the 6.62% result here.

## 14. What developers can test

A site owner who wants agents to read documents can test whether the intended client receives the right text at a stable address. A site offering API access can describe its operations, inputs, errors, and required permissions, then test a request against each operation.

An `llms.txt` file, a Markdown page, or an API catalogue is a change to test. Its value depends on whether the client finds and uses it to finish the task. This study did not measure the benefit of adding those resources, so it cannot recommend them as requirements for every site.

Agent developers need enough information to distinguish a failed connection, an unrelated page, and a valid reply in a format their software cannot read. Saving the requested address, status, redirects, content type, and reply makes that possible. A single score loses the details needed to decide whether to retry, try another address, or fix the reader.

## 15. Testing whether agents finish the work

A further study could give direct-request and browser agents the same tasks. Each task needs a correct answer or a defined website change that someone can check independently. Both passing and failing domains must be included. Testing only sites that pass would hide useful sites the checklist misses.

The agents need comparable access and permissions, repeated attempts across high and low scores, and saved replies and errors. The cases used to develop checks must stay separate from the final test cases. Otherwise, a check could look useful because it was chosen to fit results already seen. A proposed readiness score would need testing against completed tasks across languages and kinds of websites.

The [data summary](/data/agentready-study.json) supports this essay's figures and tables. The [selection supplement](/papers/agentready-check-selection.txt) explains each check's purpose and limits. Repeating the full analysis requires the individual domain records, which are kept separately. These downloads contain no original replies, because those were not saved. The current [single-domain tool](/scan) can use different rules from the September code.

To call a site ready for an agent, name the task and check that the agent completes it correctly.
