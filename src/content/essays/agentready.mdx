Ask ChatGPT to buy the cheapest noise-cancelling headphones under $200 and it reads reviews, compares prices, and hands you a shortlist. What you never see is the friction underneath. In this scan, neither of two crawler-user-agent probes was classified as an HTTP-200 success for 54.37% of sampled roots. That can mean a non-200 response, timeout, connection problem, or another failed fetch; it does not prove intentional blocking. I measured the public signals across 50,000 domains, applying the same 61 checks to every sampled root. The final recorded mean score was 25.7 out of 100.

## What I measured, and why those things

An autonomous agent performs six consecutive jobs on a website: it finds the origin, reads its content, invokes tools, relies on secure transport, cites facts, and executes payments. The audit framework maps directly to these steps across six layers:

1. **Discovery (13 checks):** `robots.txt` AI crawler rules, [`llms.txt`](https://llmstxt.org/) index specifications, `llms-full.txt`, ARD catalog (`/.well-known/ard.json`), [RFC 9727 API Catalog](https://datatracker.ietf.org/doc/rfc9727/), `agents.txt`, and XML/JSON sitemaps.
2. **Access (9 checks):** Markdown content negotiation (`Accept: text/markdown`), `.md` static URL twins, AI-specific robots meta tags (`max-snippet`, `max-image-preview`), SSR no-JS fallbacks, and `RateLimit-*` HTTP response headers.
3. **Usability & MCP (10 checks):** Live [Model Context Protocol (MCP)](https://modelcontextprotocol.io/) HTTP endpoints (`/.well-known/mcp`), [OpenAPI 3.1](https://spec.openapis.org/oas/v3.1.0) specifications with concrete parameters, machine authentication guides (`/auth.md`), and [RFC 8414 OAuth Metadata](https://datatracker.ietf.org/doc/html/rfc8414).
4. **Security (11 checks):** HTTPS enforcement, [HSTS Preload](https://hstspreload.org/) (`max-age=63072000; includeSubDomains; preload`), Content Security Policy (CSP), `X-Content-Type-Options: nosniff`, [RFC 9116 security.txt](https://datatracker.ietf.org/doc/html/rfc9116), and HTTP Message Signatures ([RFC 9421](https://datatracker.ietf.org/doc/html/rfc9421)).
5. **SEO & Citations (15 checks):** Standard title/meta tags, [JSON-LD `@graph`](https://json-ld.org/) entity schemas (`Organization`, `WebSite`, `Article`), E-E-A-T `sameAs` authority links, inverted pyramid content structure, and active RSS/Atom feeds.
6. **Payments (3 checks):** [L402 / HTTP 402](https://l402.org/) payment headers, [WebLN](https://webln.guide/) wallet discovery, and machine terms of service (`/terms-of-use.md`).

Each check uses a fixed automated rule over ordinary HTTP responses. No logins, browser rendering, or manual rating. Some checks use several probes, and a `pass` status can still represent partial credit.

- Ranks 10,001 to 100,000 (20,000 randomly selected domains)

## The headline adoption numbers

The public web shows minimal adoption for machine-specific standards:

- **llms.txt catalog:** 6.62% receive a scanner `pass` status at the tested paths.
- **Markdown probe:** 2.95% return a Markdown-like response to one `Accept` probe.
- **Basic MCP screen:** 1.82% return an HTTP-2xx body containing `jsonrpc` at one of two guessed paths.
- **OpenAPI marker:** 0.16% match an OpenAPI or Swagger marker in the selected candidate response.

An `llms.txt` file is a plain Markdown file outlining core site URLs. Content negotiation uses standard HTTP headers supported by web servers for decades. Yet 75.4% of audited origins score below 30 out of 100, and only 4 domains in 50,000 reach a score above 85.

These findings align with independent research. Server-side log analysis from [137,000 Ahrefs-monitored domains](https://ahrefs.com/blog/llmstxt-study/) recorded that 97% of published `llms.txt` files received zero requests over a 30-day window.

## Measurement methodology and rate limits

Scanning 50,000 origins without triggering network artifacts requires careful rate control:

- 34 parallel probes per domain with a 4,500ms timeout per request.
- Maximum concurrency capped at 3 target domains simultaneously.
- Standardized custom User-Agent identifying the crawler and purpose.

The final corpus is a two-wave, latest-result record. Every initial row scoring 10 or below received another scan; higher-scoring rows did not. This outcome-dependent refresh raised the mean from 22.7 to 25.7, so the final value is not a clean one-time snapshot.

## Layer-by-layer breakdown

Measuring readiness across functional layers highlights where infrastructure succeeds and where machine support lags:

1. **Security (Mean: 41.0 / 100):** Transport security headers (HTTPS, HSTS, basic CSP) carry over directly from browser-focused web standards.
2. **SEO & Citations (Mean: 28.9 / 100):** Basic meta tags and JSON-LD structured data are common on commercial sites, though missing on utility endpoints.
3. **Access (Mean: 23.9 / 100):** While static pages allow standard crawling, Markdown mirrors (`.md` twins) and explicit `RateLimit-*` headers remain rare.
4. **Discovery (Mean: 20.7 / 100):** `robots.txt` is common, but machine discovery formats (`llms.txt`, ARD catalogs) are infrequently deployed.
5. **Payments (Mean: 9.8 / 100):** Programmatic payment headers (L402 / HTTP 402) and machine Terms of Service are almost nonexistent outside specialized crypto/developer services.
6. **Usability & MCP (Mean: 7.4 / 100):** Interactive tool interfaces and machine API contracts represent the lowest-scoring category.

## WAF rules and policy contradictions

Comparing `robots.txt` declarations against HTTP response status codes reveals a major configuration gap:

<Figure
  src="/images/essays/agentready-policy.svg"

- **Explicit Allow Policy:** Among 21,881 domains whose `robots.txt` explicitly allows AI crawlers, 21.1% (4,619 domains) still block those same crawlers with HTTP 403, 429, or 503 status codes at the WAF/CDN layer.
- **Explicit Restrict Policy:** Out of domains restricting AI crawlers in `robots.txt`, 28.4% still serve full page content over HTTP without enforcement.
- **No Declared Policy:** Among origins with no AI-specific rules, 82.4% block AI crawler identities at the edge.

This mismatch occurs when security teams manage WAF settings independently from marketing or engineering teams updating `robots.txt`.

## Platform-driven adoption patterns

The 910 basic MCP-screen passes are not proof of conforming MCP services, available tools, or authentication. Only 3 rows passed the stricter saved status for `result.capabilities`, and response bodies were not retained for later review.

## Takeaways by role and domain

Different teams face distinct priorities when upgrading origins for machine consumers:

- **Full-Stack & Frontend Engineers:** Add Markdown negotiation (`Accept: text/markdown`) middleware and ensure static SSR HTML fallbacks exist without client-JS rendering dependencies.
- **SEO & Growth Specialists:** Maintain structured JSON-LD `@graph` entity graphs and publish an `llms.txt` index to preserve citations in AI search products.
- **Security & Infrastructure Engineers:** Test the exact crawler clients and network conditions they intend to support; this scan cannot distinguish blocking from transport failure.
- **Product Managers & Founders:** Prioritize platform-level defaults over one-off custom integrations. Frameworks and hosting platforms move adoption faster than custom code.
- **AI & Agent Developers:** Design agents to handle high HTTP refusal rates gracefully and rely on explicit `RateLimit-*` headers to pace requests.

## Recommended implementation steps

Site operators can improve machine readiness through four straightforward additions:

1. **Publish an `llms.txt` index:** Add a clear Markdown file at `/llms.txt` following the [llmstxt.org proposal](https://llmstxt.org/).
2. **Test Markdown responses:** If useful for your clients, support an `Accept: text/markdown` request and verify the returned representation.
3. **Align crawler policies:** Update `robots.txt` with clear directives for specific AI agents (`GPTBot`, `ClaudeBot`, `PerplexityBot`), and match WAF/CDN rules to those policies.
4. **Expose structured schemas:** Provide an OpenAPI 3.1 specification at `/openapi.json` or `/.well-known/openapi.json` with concrete parameter examples.
