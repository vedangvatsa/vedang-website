The [Model Context Protocol (MCP) tool specification](https://modelcontextprotocol.io/specification/2025-06-18/server/tools) includes a weather reply written as a sentence. It also describes returning weather values in named fields. Both fit the protocol. A language model can read the sentence, while another program can use the fields without first extracting the temperature from prose. That choice raises a question about agents talking to other agents: how much of the exchange needs to be expressed in human language? The protocols already support several answers. The harder work is deciding which information belongs in sentences, which belongs in agreed data fields, and whether some exchanges can use representations that people do not read directly.

## 1. English can sit inside a machine protocol

An agent can send a JSON message whose main content is an English paragraph. JSON provides the outer structure; the paragraph supplies the request, answer, or explanation. The same format can carry dates, identifiers, numerical results, or text in another language. Using JSON therefore does not, by itself, mean that agents have stopped communicating in prose.

The distinction matters because several separate choices often get called a protocol. HTTP carries web requests and replies. JSON is a way to encode data. [JSON-RPC](https://www.jsonrpc.org/specification) defines how to name a remote operation, supply its parameters, and match a reply to a request. An application then decides what the operation and its contents mean. An API, or application programming interface, defines how one program can request data or actions from another.

| Part of the exchange | Question it answers | Examples |
|---|---|---|
| Connection | How does information reach the other system? | HTTP, streaming connections |
| Message structure | How are requests, replies, and errors arranged? | JSON-RPC, A2A messages |
| Content | What information is being exchanged? | A sentence, an offer, a file, a vector |
| Shared meaning | How should the receiver interpret that content? | Units, schemas, domain definitions, model agreements |

In this essay, moving beyond English means reducing the need to turn known information into free-form sentences at every step. A price can remain a price field as it passes from a catalogue to a comparison tool. A task can report its status through an agreed value. An explanation can remain text when another model or a person needs to interpret it.

Some machine messages will still contain English words as field names. That does not make them equivalent to conversation. A program reading `temperature_c` follows a defined field contract. A model reading "it feels warmer than yesterday" must infer what the sentence means in context. The two forms ask different things of the receiver.

## 2. MCP connects models and applications to tools

The Model Context Protocol, or MCP, gives applications a common way to work with tools and other resources supplied by servers. A tool is a callable function, such as a database lookup or a weather search. Its description helps a model decide when to use it; its input schema defines the values the function accepts.

The client, meaning the application making the request, can ask a server for its available tools and call one by name. The function does not need an English instruction each time if its arguments already specify the work. A server exposing an illustrative `get_weather` tool with a `location` argument could receive this call:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "get_weather",
    "arguments": { "location": "Paris" }
  }
}
```

The name of the tool and the city carry the request. The application does not need to compose "Please look up the current weather in Paris" and then ask another program to interpret that sentence. The model may still use language when choosing the tool, combining its result with other information, or answering the user.

MCP also supports structured tool results. The following illustrative reply combines a readable sentence with values that code can use directly:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "content": [
      { "type": "text", "text": "The temperature in Paris is 22 degrees Celsius." }
    ],
    "structuredContent": {
      "location": "Paris",
      "temperature": 22,
      "unit": "C"
    }
  }
}
```

The temperature is fictional. The example shows a representation choice, not a measured advantage. A charting function can read the number and unit, while a language model can use the sentence. MCP's cited tool specification also allows an output schema, so the client can check the shape of structured results. The protocol supports this mix rather than requiring every response to become a conversation.

## 3. A2A connects independently built agents

Agent2Agent, or A2A, concerns exchanges with another agent system. The remote system may choose its own tools and methods. The caller needs an interface for requesting work and receiving results, without access to that system's internal model or implementation.

[A2A's core concepts](https://a2a-protocol.org/latest/topics/key-concepts/) include Agent Cards, messages, tasks, and artifacts. An Agent Card describes a system's skills, address, and access requirements. A message contains parts that can hold text, files, or structured data. An artifact is an output, such as a document or a data object. These structures allow more than a plain chat transcript.

The content parts of a hypothetical message could combine a request with machine-readable inputs. Only the parts are shown here; a complete message also includes the fields required by its protocol version.

```json
[
  { "text": "Compare the forecasts for these cities." },
  {
    "data": {
      "cities": ["Paris", "Lyon"],
      "temperature_unit": "C"
    },
    "mediaType": "application/json"
  }
]
```

The text states the open-ended job. The fields specify the cities and unit. The receiving agent can return a written comparison, a structured table, or both. It can also ask for more information if the requested comparison needs a date or another missing input.

[A2A's task model](https://a2a-protocol.org/latest/topics/life-of-a-task/) supports work that continues beyond one reply. A task can report progress, require more input, or reach a final state. This separates communication about the work from the content produced by it. A large file, a partial result, and a final status do not need to be packed into one paragraph.

The protocol gives agents a shared procedure for exchanging work. It does not prescribe one language for every task. A research agent may need a detailed explanation from another researcher; a scheduling agent may need a list of available time slots. The appropriate content depends on the receiver and the next operation.

## 4. The surrounding protocols do different jobs

Other projects address discovery, identity, or payment messages. These functions can be combined with general-purpose tool and task protocols.

| Project or specification | Main role in the exchange |
|---|---|
| MCP | Access to tools and resources, including typed tool calls |
| A2A | Messages, tasks, and results exchanged with remote agent systems |
| ACP (BeeAI) | An earlier REST-based agent protocol that joined A2A |
| AGNTCY | Components for discovery, identity, messaging, and observation |
| AP2 | Signed checkout and payment records used to establish authority |
| x402 | Payment requirements and payment handling for HTTP resources |

The BeeAI project's [Agent Communication Protocol repository](https://github.com/i-am-bee/acp) describes messages containing different media, runs, sessions, and a REST API defined through OpenAPI. It was archived on August 27, 2025, and its notice says ACP is now part of A2A. Combining protocol work does not, by itself, give every application the same data definitions.

[AGNTCY](https://docs.agntcy.org/) is a collection of components. Its documentation includes an agent directory, the Open Agentic Schema Framework (OASF) for describing capabilities, identity services, and Secure Low-Latency Interactive Messaging (SLIM). These help systems find and connect to one another. They do not replace the application-level decision about how to describe a flight, a document, or a scientific result.

The [Agent Payments Protocol, AP2 v0.2](https://ap2-protocol.org/ap2/specification/), defines checkout and payment mandates and associated verification. [x402](https://docs.x402.org/introduction) uses HTTP `402 Payment Required` and payment requirements to support paid access to resources. The two can be combined, but AP2 is not another name for an HTTP 402 response. Payment information is one specialized kind of agent exchange, rather than the model for every agent conversation.

## 5. The network format does not choose the language

A2A's documentation lists [JSON-RPC, gRPC, and HTTP+JSON/REST bindings](https://a2a-protocol.org/latest/topics/custom-protocol-bindings/). A binding specifies how the protocol's operations and data appear through a particular interface. The underlying task and content can retain their meaning across those interfaces.

[gRPC](https://grpc.io/docs/what-is-grpc/introduction/) commonly uses Protocol Buffers to define services and messages. It can generate client and server code from those definitions. A binary message can contain a plain-language string, just as a JSON object can. Binary encoding changes how the information is represented on the connection; it does not automatically remove natural language from the content.

This gives three questions that need different answers. How are the bytes sent? How is the message structured? How does the receiver understand the content? Improving one layer may help speed or reliability without changing the others. A faster transport can still carry a long English explanation between two models.

The same point applies to streaming. Sending an answer in smaller pieces changes when the receiver gets it. Those pieces may contain text, data, or files. A stream of words remains a language exchange. A stream of typed status updates can support a different processing path, with code responding to events as they arrive.

## 6. Why agents still use human language

Language models already accept text and produce text. A system that gives one model's answer to another can use those interfaces directly. Developers do not have to define a separate vocabulary for every open-ended task before the models can exchange useful information.

That flexibility matters when the job changes during the conversation. An agent asked to compare research papers may discover that the studies use different definitions of success. A paragraph can explain the difference before anyone has designed a field for it. Forcing the whole discussion into a small fixed schema too early can discard information the next agent needs.

Tool use already shows how the forms can work together. A model can read a tool's description, choose it in response to a user's request, and supply structured arguments. The application then calls the tool and returns its result. Natural language helps choose and interpret an operation; the operation itself can use exact values.

Schema-constrained generation extends this arrangement. [OpenAI's Structured Outputs announcement](https://openai.com/index/introducing-structured-outputs-in-the-api/) describes constraining generated output to a supplied JSON Schema. The same announcement notes that values can still be wrong. A structured response reduces some formatting problems, while the application still needs to check whether the response answers the intended question.

English is also only one possible language at this level. A person can ask a question in another language, and text messages can carry that language. The more useful distinction is between free-form language that a model interprets and fields that a program can process under defined rules.

## 7. Earlier agent languages faced the same problem

Agent communication did not begin with language models. In [their 1994 KQML paper](https://doi.org/10.13016/m2bvis-7jvt), Tim Finin and colleagues described both a message format and a message-handling protocol for sharing information among agents. The design used named communication acts, giving software a way to distinguish different kinds of exchange.

FIPA's Agent Communication Language makes a similar separation between the act and its content. The [JADE ACLMessage API](https://jade-project.gitlab.io/API/jade/lang/acl/ACLMessage.html), an implementation of FIPA message structure, exposes acts such as `REQUEST`, `INFORM`, and `REFUSE`. It also includes fields for the content language, ontology, sender, receiver, and conversation identifier. An ontology supplies an agreed set of concepts and relationships for interpreting the content.

Those distinctions remain useful. Requesting a price is different from reporting a price. A reply belongs to a particular exchange. The receiver needs to know which vocabulary the sender uses. A transport connection alone supplies none of that meaning.

Language models offer another way to handle some of the interpretation. A receiver can work with an unfamiliar description instead of requiring every term to have been encoded in a formal vocabulary. That makes the interface more flexible, but its interpretation can be mistaken. The older requirement for shared meaning returns wherever an application needs exact behaviour.

The history therefore suggests a practical limit to format changes. Replacing an older message syntax with JSON can improve tooling and ease of use. It does not remove the work of defining a domain. The general messaging rules and the meaning of the content remain separate parts of the design.

## 8. Whole industries already communicate through fields

The [FIX Protocol](https://fixtrading.org/standards/fix-protocol/) defines trading messages, fields, and workflows for orders, executions, and market data. Its documentation separates those business definitions from transport and encoding. The same business message can use tag-value, binary, or JSON representations without changing its intended meaning.

That is a useful model for routine agent exchanges. An order does not need to be rewritten as a fresh explanation every time it crosses a system boundary if both sides already understand its fields. The shared definitions, not the absence of prose alone, make that possible.

[ISO 20022](https://www.iso20022.org/faq) likewise maintains a financial data dictionary and business process catalogue. It supplies a method for developing messages as well as the definitions used in them. Calling it an XML format misses much of the work that makes the messages usable across institutions.

Healthcare shows why structured communication need not eliminate text. [HL7 FHIR](https://www.hl7.org/fhir/narrative.html) allows many resource types to contain a human-readable narrative alongside structured data. That narrative may carry relevant information beyond the fields. The receiving system needs to know which parts it can process automatically and which parts still require interpretation.

The same split can apply to agents. A service can return an exact observation together with a note about missing context. An analyst agent may need both. A charting function may use only the numerical values. Moving beyond conversational messages is most useful when it follows the needs of those receivers, rather than treating every sentence as waste.

## 9. Shared schemas make direct exchange possible

The field `price` is not enough to establish whether a value is per item, per passenger, or for the entire order. It also needs a currency and a definition of which charges are included. The word `refundable` can hide differences between cash, credit, fees, and deadlines. Agents can exchange those labels perfectly while interpreting them differently.

[JSON Schema](https://json-schema.org/understanding-json-schema/reference/object) can require properties and restrict their types and allowed values. It gives software a way to reject a malformed object or a missing required field. Domain definitions supply the next layer: what those fields refer to and how they fit together.

A useful exchange also needs to distinguish observations, estimates, and unknowns. A missing delivery date should not silently become tomorrow's date when a model summarizes a response. A system can preserve an explicit unknown or attach the source of an estimate. These choices make the data easier to reuse without repeatedly asking another model to reconstruct its meaning from a paragraph.

Versions matter as these definitions change. If a supplier changes a field from base price to total price, an older receiver may still read the number successfully and use it incorrectly. The parties need a way to identify the version and agree on any conversion. This is part of communication, even when the message contains no natural-language sentence.

Open, stable definitions can make independent agents easier to connect. A private schema can work well inside one company, but an outside agent needs its documentation or an adapter. Protocol support and shared meaning therefore need to develop together if typed exchanges are to travel beyond one platform.

## 10. The case for shorter, more direct messages

A repeated exchange can create unnecessary work when one model turns known fields into prose and another extracts the same fields again. Passing the values directly can avoid that translation. It can also make simple filtering and calculations possible in ordinary code, without asking a model to interpret each result.

The saving is not automatic. JSON can repeat long field names, and supplying a schema can add to a model's input. A compact identifier saves space only when the receiver can obtain the record it names. Removing an explanation can reduce message length while also removing information needed for the task.

Costs need clear units. Bytes sent over a connection differ from tokens processed by a model. Tokens are pieces of text, such as words, word fragments, or punctuation. Network compression can reduce transmitted bytes without reducing the model input after the application reads the message. A comparison should count the actual representation used at each stage.

The whole interaction matters too. Setup, tool descriptions, clarification rounds, retries, and recovery can outweigh a shorter individual message. A fair test gives both designs the same task and information, then measures correct results, time, and total cost. A fixed claim that an English plan takes thousands of tokens while a data object takes eighty needs evidence from a defined comparison.

The economic reason to move some exchanges away from prose is therefore specific. Routine, well-defined information can often be handled directly. Open-ended reasoning may still justify the cost of an explanation. The useful boundary depends on the task and the receiving system.

## 11. Learned representations go further than structured text

JSON fields still use symbols whose meanings people define. A learned representation takes a different approach. A model turns information into numerical values whose use depends on its training. Other compatible components can work with those values without first receiving a full natural-language account.

An embedding is one familiar example. [Text embeddings](https://platform.openai.com/docs/guides/embeddings) support tasks such as retrieving related documents or grouping similar items. An agent could pass such a representation to a compatible search system. That is different from assuming that the vector expresses a complete instruction in a universal language.

Research also examines communication through model states. [HyLaT](https://arxiv.org/html/2605.25421v1), a May 2026 research paper, trains agents to exchange latent vectors alongside short text outputs. Its main experiments use a shared Llama model, with a two-stage training process and tests on question-answering tasks. The authors report lower generated-token counts and running time than their trained text baseline, with accuracy varying by task. They also test a pair of different model families using learned adapters.

That is evidence for a trained hybrid method under the tested conditions. It does not establish a common latent language that unrelated commercial agents can use without preparation. Its generation counts also do not, by themselves, measure network bytes or commercial API charges. Those are separate questions when assessing an implementation.

| Representation | What the receiver needs |
|---|---|
| Natural-language text | A way to interpret the language and context |
| Structured data | Agreed fields, types, units, and definitions |
| Embedding or model state | A compatible representation, model or adapter, and tested use |

A2A can carry structured JSON values and file content, so transporting numerical arrays is possible. Transporting them does not make their coordinates meaningful to another model. Compatibility may require the same encoder, an agreed version, additional training, or a learned conversion between systems.

This creates a plausible difference between tightly connected agents and an open network. A group trained together can develop an efficient internal exchange. Independent services may prefer text and published schemas because new participants can understand them with less preparation. Both forms can exist, with a human-readable or structured interface at the boundary.

## 12. What people can still read

A move away from English changes how people inspect an exchange. A JSON object is readable if its fields are documented. A binary message can be rendered through its schema and decoder. Learned model states are harder to explain directly because the meaning is not laid out as named fields or sentences.

Unreadability should not be mistaken for privacy. [Morris and colleagues](https://arxiv.org/abs/2310.06816) showed that text could be reconstructed from embeddings in the settings they tested. A list of numbers is not automatically anonymous or encrypted. The choice of representation needs to account for the information it may reveal as well as the information a receiver can use.

People also need a clear account of what an agent did. That account can be generated from recorded requests, responses, task states, and results. It should stay linked to those records, so a readable summary can be checked rather than accepted as a fresh story about an invisible process.

Permissions remain part of this exchange, especially when agents purchase resources or act through another service. Signed records, identity checks, and action limits address who may do what. They accompany the communication problem; they do not decide whether the task description belongs in English, structured fields, or a learned representation.

## 13. A mixed language for the agent web

The likely direction is a mix of communication forms, chosen for the work involved. Natural language gives people and models room to explain unfamiliar goals and exceptions. Structured messages give software exact values for repeatable operations. Learned channels offer another option where compatible models and training make them useful.

MCP, A2A, and related projects provide parts of the machinery for these exchanges. They make tools, remote tasks, discovery, and specialized messages easier to connect. Their existence does not mean that every participant already shares the same vocabulary or that one representation will replace all the others.

An agent may eventually carry out much of a routine task without composing a paragraph for every other agent it contacts. People can still state their goals in ordinary language and receive a readable explanation at the end. The communication between those points can use whichever forms preserve the needed information and have been tested for the task.

A useful sign of progress would be a task moving between independently built agents without repeatedly turning known facts into prose and back again. The systems would exchange the values and results directly, while leaving people enough information to understand the work. That is the change worth examining when agents stop speaking English to one another.
