MCP, [Anthropic's Model Context Protocol](https://www.anthropic.com/news/model-context-protocol), is how an agent calls tools. A2A, [Google's Agent-to-Agent Protocol](https://a2a-protocol.org), is how agents find each other. People keep comparing both to HTTP. I counted what I could: npm and pypi downloads, GitHub stars, and whether 28 large sites publish the discovery files these protocols need.

Do not rank them on one table. MCP is an internal plug. A2A is a public handshake. Mix the jobs and 198 million npm downloads will look like A2A lost a fight it was not in.

## Why they exist

Agents need tools to act, and they need other agents to coordinate. Without a shared way to describe tools, every vendor ships a private plug, integration costs rise, and switching gets harder. MCP is the tool plug. A2A is the agent-to-agent talk.

MCP: An MCP server exposes tools and resources. An MCP client, inside an agent host, calls them. Anthropic released it as an open standard in [November 2024](https://www.anthropic.com/news/model-context-protocol). Major model vendors and cloud platforms shipped SDKs and connectors around it.

A2A: A company publishes an agent card at a well-known path. Another agent reads it and knows how to start talking. Google [announced it in April 2025](https://developers.googleblog.com/en/a2a-a-new-era-of-agent-interoperability/) with over 50 partners and [handed it to the Linux Foundation](https://developers.googleblog.com/en/google-cloud-donates-a2a-to-linux-foundation/) in June 2025. Putting a JSON file on a domain is easy. Deciding to expose an agent is not.

I can count public installs and files on the open web. I cannot count what runs inside a VPC.

## What was measured

Three sources, all queried in the week of 13 August 2026.

**npm and pypi registries.** Monthly download counts from the [npm downloads API](https://github.com/npm/registry/blob/main/docs/download-counts.md) and [pypistats](https://pypistats.org/) for the protocol SDK packages. [`@modelcontextprotocol/sdk`](https://www.npmjs.com/package/@modelcontextprotocol/sdk) and [`a2a`](https://www.npmjs.com/package/a2a) at npm. [`mcp`](https://pypistats.org/packages/mcp) and [`a2a-sdk`](https://pypistats.org/packages/a2a-sdk) at pypi. For context, [`anthropic`](https://pypistats.org/packages/anthropic) and [`openai-agents`](https://pypistats.org/packages/openai-agents) at pypi were also queried.

**GitHub stars.** Star counts from the GitHub API for [`modelcontextprotocol/servers`](https://github.com/modelcontextprotocol/servers), [`modelcontextprotocol/modelcontextprotocol`](https://github.com/modelcontextprotocol/modelcontextprotocol), and [`openai/openai-agents-python`](https://github.com/openai/openai-agents-python). The `google/A2A` repository was not reachable through the API at the time of query.

**Direct domain crawl.** A headless browser made GET requests to 28 top-consumer and top-enterprise domains for four discovery files. `/.well-known/agent-card.json` for A2A discovery. `/agents.txt` for the agents-txt.com convention. `/.well-known/mcp/server-card.json` for an MCP draft path. `/.well-known/ai` for an IETF draft. Every status-200 response was verified for actual content, not a soft-404 catch-all page. The crawl also checked `/llms.txt` as a benchmark.

Twenty-eight domains is a sample, not a census. They are big consumer and enterprise sites. Enough to see whether discovery files sit on sites people already use. Not enough to prove the files are absent everywhere. When the count hits zero later, that is zero on these 28, not zero on the internet.

Package names can collide or under-count. The `a2a` npm package misses companies that vendor code or use another name. Treat the gap as order of magnitude, not a headcount of developers.

Downloads are not users. They include CI, automated builds, and cache misses. A popular transitive dependency can inflate the total without anyone choosing the protocol on purpose. Order of magnitude still matters. MCP is infrastructure. A2A, on npm, is not.

Cloud providers and AI companies ship the MCP SDK as a dependency. Install OpenAI, Anthropic, or Google agent stacks and you can increment the MCP count. That is adoption of a dependency graph. It is not a million teams writing new MCP servers from scratch.

Stars are weaker. They measure bookmarks. The MCP servers repo's stars mean people want ready-made tool servers. Missing A2A star data is a hole in the table, not a score against A2A. I left the cell empty.

## The server gap. Zero discovery files on top sites

A2A needs agent cards at `/.well-known/agent-card.json`. MCP's draft path is `/.well-known/mcp/server-card.json`.

The crawl of 28 domains found zero real agent cards. Twenty-seven of the 28 returned either 404 or a soft-404 HTML error. LinkedIn and Netflix returned status 200 but delivered HTML, not JSON. Zero agent cards. The `/agents.txt` companion convention similarly returned zero real deployments. Every 200 was an HTML catch-all on content-type verification. The MCP server card and `/.well-known/ai` were zero across all 28 domains.

Zero cards here does not mean zero cards on the internet. It means none of these large sites published one I could verify.

Most of them do not run a public agent endpoint for strangers. They run apps, keyed APIs, and support chat widgets. A2A discovery needs a brand to advertise an agent on the open web. Those brands have spent years blocking bots and scrapers. An agent card is a product and security call, not a missing line in a config file.

MCP does not need a well-known file on stripe.com to work. Servers already spread through [Smithery](https://smithery.ai) and GitHub lists. A2A does need a card if strangers are supposed to find the agent. Empty well-known paths on big sites hurt A2A more than they hurt MCP.

The 12-to-14 range reflects text/plain responses starting with a blank line. Confirmed deployments include GitHub, Cloudflare, Atlassian, Stripe, Shopify, Notion, WordPress, MongoDB, Dropbox, Slack, and Vercel.

llms.txt has no vendor backing. It was created by [Jeremy Howard of Answer.AI](https://llmstxt.org) in 2024. A2A has Google, the Linux Foundation, and [announced support from over 100 enterprises](https://developers.googleblog.com/en/google-cloud-donates-a2a-to-linux-foundation/). The discovery file without vendor backing is the one with observable deployments on top sites.

llms.txt tells a model how to read a site. No agent endpoint. Cheap. An A2A card that points at a live agent is a security review. Sites will post a text file. That is not evidence they will post an agent next.

## What the numbers mean

MCP is widely adopted infrastructure. A2A's discovery layer is not in consumer-facing production on these 28 sites. That matches the jobs: one is a tool plug, the other is a public handshake.

An agent that searches a database, sends an email, or queries an API calls an MCP server. Thousands of those servers sit in registries and GitHub lists. The SDK downloads are a protocol that standardized internal tool calling.

A2A asks which agent a site exposes. That needs an endpoint and a published card. Most of the 28 sites have neither. The SDK exists, mostly in Python.

MCP shipped in November 2024. A2A went to the Linux Foundation in mid-2025. Empty well-known paths after a year do not mean the protocol failed. I crawled in August 2026. Ship a card and the next pass will catch it.

A company can run A2A on a private network and never publish a card. I would miss that. This is an open-web count, not a count of internal meshes.

## Security and product reasons for slow discovery

Publishing an agent card is not free.

A public agent endpoint expands attack surface. Prompt injection, tool abuse, data exfiltration, and denial of wallet are live concerns for any agent that can act. Large firms already fight bot traffic on login and search pages. Asking them to advertise an agent that can take actions is a hard sell for security teams.

Product incentives also cut against early public cards. Many firms want agents inside their authenticated product, not agents that other vendors' agents can call on equal footing. A2A's interoperability story is strongest for users. It can be weakest for firms that monetise exclusive assistant surfaces.

Open-web discovery is slower than SDK installs. Tooling teams already wanted a plug. Security teams do not already want a public agent. That is why the download table and the crawl disagree.

## HTTP is the wrong poster

People reach for HTTP because a shared request language is easy to sell. Agents do need shared shapes. Otherwise every integration is custom.

HTTP rode on pages companies already wanted online. An agent card asks them to publish something that can act, closer to a customer-service API than an About page. Agreeing on JSON is easy. Agreeing to expose the agent is not.

MCP is closer to HTTP inside a company. Teams already want the agent to call tools. A2A is closer to letting another firm's software dial your support desk. That market exists. It starts smaller.

## What "adoption" should mean

Adoption splits into four layers.

1. **Spec existence.** A public specification and a governance home.
2. **SDK installs.** Developers can import a library.
3. **Server or agent supply.** Someone runs endpoints that speak the protocol.
4. **Open discovery.** Strangers can find those endpoints without a private sales call.

MCP shows strength on layers 1 to 3 in public evidence. Layer 4 is weak on brand domains, and less necessary if registries carry supply. A2A shows strength on layer 1, partial strength on layer 2 in Python, and no verified strength on layer 4 in the 28-domain sample. Layer 3 may exist privately. Private meshes are not visible to this method.

Partner announcements sit beside these layers, not above them. Fifty or a hundred logos on a launch blog are layer-1 politics. They are not layer-4 evidence.

## Registries versus well-known paths

The internet has solved discovery more than once. DNS. Search engines. App stores. Package registries. Well-known URIs.

MCP's early gravity pulled toward registries and GitHub lists. That path matches how developers already install tools. It also centralises curation and trust questions in whoever runs the registry. A2A's agent-card path pulls toward domain-controlled discovery, which matches how organisations already prove ownership of a hostname. That path keeps control with the brand and demands that the brand opt in.

llms.txt succeeded on brand domains partly because it is static and low risk. An agent card that points to a live agent is dynamic and higher risk. Expecting A2A cards to spread at llms.txt speed was never a good prediction. Expecting some brand to ship one card if the product case is clear remains fair. The sample says that case has not cleared production on the measured domains yet.

## False zeros and how they are avoided

A simple crawler treats HTTP 200 as success. Many large sites return 200 with an HTML error page for unknown paths. Those were rejected by checking content type and body shape. LinkedIn and Netflix did that in this sample: HTTP 200, HTML body.

Another false zero comes from redirects through consent or bot walls. A headless browser can see a different answer than curl. The crawl used a headless browser for that reason. Even then, geo fences and account walls can hide files from a research crawl while showing them to a logged-in partner agent. The method under-counts protected deployments by design.

A false positive is also possible. A site could serve a toy JSON file that matches the path and fails the protocol schema. This pass required real content rather than a full schema validate against every A2A revision. Later audits should pin a schema version and validate strictly.

## What a second pass should add

The August 2026 pass is a baseline. Later passes should keep the same 28 domains for trend, add developer-native domains such as docs sites and cloud consoles, sample any public A2A registry that appears, and try to separate direct MCP imports from transitive installs if registry metadata allows.

## What to do with these results

Internal agents: MCP is already in a lot of default stacks. Worry about server quality, auth, logging, and what the tools are allowed to do. Downloads will not tell you that.

Cross-company agents: ignore the launch blog. Ask for a live card or a directory entry you can call. If they cannot show either, you are doing a partnership, not adopting a public protocol.

Site owners: llms.txt is cheap and already common on this list. An A2A card is an API launch. Budget the review.

Do not call spec plus logos plus SDK plus discovery one word, "adoption." That is the same trick as treating a $500 billion ceiling as cash.

## Limits

A2A people can say the protocol is young, enterprise meshes are invisible to a public crawl, and discovery takes years. MCP people can say download counts overstate conscious adoption when the SDK is transitive. Both are true, and both are already in the method notes.

Open-web discovery may never be how agents find each other anyway. Agents may find each other through marketplaces, signed partner directories, or OS-level assistants, not well-known JSON on consumer domains. If that happens, the zero on these 28 sites is a footnote, not the story.

## What would change the numbers

A major consumer or enterprise brand in the crawl serving a valid agent card at `/.well-known/agent-card.json` would move the A2A count off zero. If MCP's draft server-card path gets deployed on brand domains, the crawl could detect it. Today MCP mostly spreads through registries and GitHub lists rather than well-known paths. A public registry of live A2A agent cards, with endpoints an outsider can call, would let adoption be measured without crawling. No such registry turned up during this pass.

The SDKs are installed. On these 28 sites, nobody published the files that would let a stranger's agent find them. That is an internal tool protocol with a large download count, and a public-internet protocol with no cards I could fetch.
